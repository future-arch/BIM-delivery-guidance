# 总则

### 为规范建筑信息模型交付，提高建筑信息模型的应用水平，制定本标准。
> 本条文明确了制定本标准的目的。

### 本标准适用于工程建设项目全生命周期内，应用建筑信息模型方法和技术进行信息的组织、生产与交付。
> 本条文规定了本标准的适用范围。建筑信息模型（building information modelling, BIM）既是一种方法，也是一项技术，通过数字化的手段实现信息交付，从而实现信息的应用价值，这是一个横跨项目全生命周期、涵盖多参与方协同的复杂过程。所交付的信息质量的保证，有赖于信息的组织与生产）的规范与协同。交付过程通常以信息需求为导向，由信息的组织、生产与交付等环节共同构成持续的管理过程。

### 建筑信息模型交付，除应符合本标准外，尚应符合国家现行有关标准的规定。

# 术语

### 信息交付 information delivery

信息提供方按照约定要求向信息需求方移交工程信息的活动。

> 本术语既包括工程阶段之间的成果移交，也包括同一阶段内参与方之间受控的信息传递。在语义明确时，可简称为“交付”。

### 信息需求 information requirement

为实现特定业务目标而对所需信息提出的要求。

> 本术语参考 ISO 29481-1:2025 中 information requirement 的有关规定。信息需求通常依据特定信息用例提出，并可随项目进展予以细化和调整。

### 信息生产要求 information production requirements

为满足信息需求而对信息生产活动及其成果提出的具体要求。

> 信息生产要求是对信息需求的进一步落实，用于指导有关参与方开展信息生产。

### 交付成果 deliverable

按约定要求移交给信息需求方的工程信息集合。

### 工程对象 engineering object

建筑工程中构成工程本体或服务于工程建造的实体对象和逻辑对象的统称。

### 模型单元 model unit

建筑信息模型中承载工程对象数据的基本组成单元，是工程对象的结构化数字表述。

> 模型单元是工程对象在建筑信息模型中的数字化映射，按项目级、功能级、构件级和零件级嵌套组成层级化的模型架构。模型单元通过几何信息和文字信息两个维度描述工程对象的特征，例如一扇窗户，其三维形体为几何信息，其材质、尺寸参数、价格等为文字信息。

### 模型架构 model framework

组成建筑信息模型的各级模型单元之间组合和拆分等构成关系。

> 在分解模型单元时，不同的工程信息需求会产生不同的分解方式，另外随着工程阶段的发展，对建筑的描述趋于丰富和详尽。模型单元也趋于细微，从而产生“最小模型单元”的概念。模型单元级联整合形成本体信息模型，而面向具体业务的应用则产生业务信息模型。

### 数据项 data item

工程定义数据集中不可再分的结构化数据的最小单位。

### 数据表 data sheet

按预定义结构组织工程对象属性数据的结构化记录。

> 数据表是属性数据的表格化载体。数据表的结构可由数据模板定义，也可采用其他预定义的组织方式。

### 电子文件 electronic file

在数字设备及环境中生成，以数码形式存储，依赖计算机等数字设备阅读和处理的文件。

> 本定义参考现行国家标准《电子文件归档与电子档案管理规范》GB/T 18894的有关规定。

### 信息用例 information use case

为实现特定业务目标，对工程信息的用途、参与角色、所需信息及预期成果所作的规定。

> 信息用例用于说明“为何使用信息、由谁使用信息、需要何种信息以及形成何种成果”，是提出信息需求、组织信息交付和确定交付成果的重要依据。

### 信息生产计划 information production plan

为落实信息生产要求而对信息生产活动作出的安排。

> 信息生产计划用于组织信息生产的实施，是开展信息生产、协同和检查的依据。

# 基本规定

### 建筑信息模型交付应贯穿工程项目各阶段，并应以信息用例为导向、以信息需求为依据、以信息组织为基础，开展交付准备、信息生产、交付和验收等工作。

> 本条是对建筑信息模型交付总体技术路线的概括。建筑信息模型交付不是单一成果移交行为，而是从信息需求识别到成果验收的连续管理过程。其基本逻辑是：根据信息用例提出信息需求，据此确定信息生产要求并编制信息生产计划，再组织信息生产、交付和验收。将信息组织置于全过程前端，是为了使后续工程定义数据集、元数据、交付成果及协同流程建立在统一规则基础上，便于工程项目各阶段和各参与方之间有序衔接。

### 工程项目全生命周期中，信息交付应以满足信息需求和支持信息用例为目标，并应符合下列要求：

#### 应具有真实性，即信息内容应反映工程对象的设计意图、客观物理状态或逻辑关系；
#### 应具有完整性，即信息内容的广度和深度应满足特定阶段协同工作、移交或应用的需要；
#### 应具有可用性，即信息内容和表达形式应能够被接收方的数据环境读取与解析；
#### 应具有有效性，即信息应保证来源可靠，且经过相应责任主体的确认与授权；
#### 应具有安全性，即应防范信息在产生、存储与交换环节遭受篡改及未授权访问。

### 应根据信息需求，对工程信息进行组织，形成工程定义数据集和元数据，并应符合下列规定：
#### 工程定义数据集应包含工程对象定义的全部信息内容及其表达形式；
#### 元数据应作为对数据项和电子文件进行标识、归档、检索和管理所需的描述性数据。

> 工程建设项目中的信息并非天然有序形成，而是分散存在于信息模型、工程图纸、数据表、文档以及各类业务过程之中。若缺乏统一组织，往往会出现同一对象多头描述、不同参与方口径不一、后续难以检索和复用等问题。本条强调，应当在信息生产之前，根据实际信息需求先行建立统一的信息组织基础，将工程对象相关信息归集为工程定义数据集，并通过元数据建立识别、检索和管理规则，以便后续信息生产、交付、应用和维护能够在同一数据基础上开展。

### 信息交付过程应由信息需求方和信息提供方事先约定，基本步骤应符合下列规定：

#### 信息需求方应根据信息用例提出信息需求；
#### 信息提供方应根据信息需求确定信息生产要求并编制信息生产计划；
#### 信息提供方应按照约定开展信息组织和信息生产，形成交付成果；
#### 信息提供方应按照约定的质量要求对交付成果进行检测和审核，审核合格后交付；
#### 信息需求方应根据信息需求对交付成果进行验收。

> 信息交付不是单纯的成果提交行为，而是信息需求方与信息提供方围绕特定信息用例所形成的协同过程。本条给出基本步骤，意在说明建筑信息模型交付应先明确“需要什么信息”，再落实“如何生产信息”，继而形成成果、完成审核并实施验收。通过这样的过程安排，可以把信息需求、信息生产和成果验收衔接起来，减少因要求不清、职责不明或验收依据缺失而造成的返工和争议。

### 信息生产、交付和验收过程中，应使用元数据对数据项和电子文件进行管理。

> 元数据是保障数据项和电子文件可识别、可追溯、可检索的重要基础。在信息生产、交付和验收过程中，若仅关注信息内容本身而忽略其标识、版本、状态、来源和责任信息，往往会导致同名文件混淆、版本失控或责任难以界定。本条强调全过程使用元数据进行管理，其目的在于使交付信息不仅“有内容”，而且“可管理、可追踪、可复核”。

### 信息用例和信息需求的提出方法、信息应用的过程和成果应符合现行国家标准《建筑信息模型应用标准》GB/T 51235的有关规定。

> 信息用例和信息需求并非孤立提出，而应与工程应用过程相对应。本条引用现行国家标准《建筑信息模型应用标准》GB/T 51235，旨在使本标准关于“交付什么信息”的规定，与“为何应用信息、如何应用信息”形成衔接。这样既可避免本标准重复规定应用方法，也有利于保持信息交付要求与实际业务活动之间的一致性。

### 工程定义数据集应作为建筑信息模型交付的数据基础，面向特定信息用例时，可在工程定义数据集基础上形成相应的工程用例数据集。

> 本条说明建筑信息模型交付中“定义”与“用例”两类数据集的基本关系。工程定义数据集用于对工程对象及其关系进行统一、稳定的数字化表述，是各类信息应用和成果表达的共同基础。工程用例数据集则面向特定信息用例，在工程定义数据集基础上按实际业务需求进行组织和调用，用于满足特定阶段、特定任务和特定管理活动的信息应用要求。

### 信息交付应在受控的通用数据环境中完成，通用数据环境应符合现行国家标准《建筑信息模型应用统一标准》GB/T 51212的有关规定。

> 建筑信息模型交付通常涉及多参与方协同、多轮次提交和多版本成果管理，若缺乏统一且受控的交付环境，容易出现成果来源不明、状态混乱、版本失配和传递失序等问题。本条要求在受控的通用数据环境中完成信息交付，其目的在于为信息传递、审核、发布和存档提供统一载体，使交付过程处于可控状态，并保证各参与方基于一致的信息来源开展工作。

### 信息生产、存储和交换过程中的信息安全应符合国家现行有关标准的规定。

> 建筑信息模型信息在生产、存储和交换过程中，既可能承载工程技术内容，也可能涉及经营管理、设施运行甚至安全保密等敏感信息。随着协同范围扩大和数字化程度提高，信息泄露、篡改、误传和未授权访问等风险更加突出。本条作原则性规定，要求信息安全管理符合国家现行有关标准，意在将信息安全纳入交付全过程管理要求之中，使信息在可共享、可应用的同时，保持必要的受控和保护。

# 工程信息组织

## 一般规定

### 工程信息组织应作为交付准备、信息生产和交付各环节的通用基础。

> 工程信息组织是整个交付流程的基础环节，为各环节提供统一的信息框架和数据规则。若各环节各自定义信息结构，容易造成数据冗余、口径不一和交付返工。本条将信息组织定位为"通用基础"，意在确保同一套信息组织规则贯穿交付准备、信息生产和信息交付全过程。

### 工程信息组织应以工程对象为基本单元，进行数字化表述和数据管理。

> 工程对象是工程信息的语义载体，以工程对象为基本单元进行信息组织，使数据结构与工程实际形成直接的映射关系——每一个构件、系统、空间等工程对象都对应一组完整的数字化描述。这一原则区别于以图纸、文件为中心的传统信息组织方式，有利于实现信息的精确检索、跨专业共享和全生命周期追溯。

### 数字化表述的组织结构应与工程对象的分解结构对应，表述内容应与工程对象的特征及信息需求对应。

> 本条强调信息组织与工程实际的双重对应关系：组织结构层面，数字化表述的层级划分（如项目—子项—系统—构件）与工程对象的功能分解和空间分解保持一致，避免信息结构与工程逻辑脱节；表述内容层面，每一级工程对象所承载的信息广度和深度由具体的信息需求驱动，不同阶段、不同用途所需的信息内容存在差异。

## 工程对象

### 工程对象依其物质实在性可划分为工程实体对象和工程逻辑对象，并应符合表4.1.1的规定。

表: 表4.1.1 工程对象的性质

<!-- @col-widths: 20, 40 -->
| 类型 | 技术含义 |
| :---: | :--- |
| 工程实体对象 | 描述具有确定建造材质与物理形态的工程组成部分 |
| 工程逻辑对象 | 描述基于功能、空间、系统或管理层级所定义的工程组成部分 |

> 工程对象是数字化表述的基本语义单元，工程实体对象与工程逻辑对象在信息组织中具有同等地位。
> 工程实体对象具有明确的建造材质与物理边界，如梁、柱、管道、设备等，是施工或制造的直接对象。
> 工程逻辑对象不表现为单一的物理实体，而是基于功能、空间或管理需求所定义的工程组成部分。例如，”一栋建筑”是由大量实体对象聚合而成的空间层次，”电气系统”是由多组物理设备连接而成的功能网络，”防火分区”是满足安全管理需求划定的三维区间界限，均属于典型的逻辑对象。
> 本标准中的工程对象在概念上与ISO 23387:2025中的”对象（object）”相对应，即”可感知或可构想的世界的任何部分”，涵盖设计对象、产品、工具设备、系统、空间、建筑等。在基于ISO 12006-3的数据字典中，工程对象的类型定义对应于”主题（subject）”概念。

### 工程对象应按建设活动及其产出划分为工程本体和施工资源两大类别，工程对象的主要类别和类型宜符合表4.1.2的规定。

表: 表4.1.2 工程对象的主要类别和类型

<!-- @col-widths: 20, 40 -->
| 类别 | 工程对象类型 |
| :--- | :--- |
| 工程本体 | 构件和产品 |
|  | 由一组构件和（或）产品形成的系统 |
|  | 具有特定功能的区域和空间 |
|  | 由构件、系统、区域和空间共同构成的项目整体 |
| 施工资源 | 机械设备 |
|  | 临时设施 |
|  | 施工材料 |

> 本条将工程对象划分为”工程本体“和”施工资源“两大类别。工程本体是建设活动的最终产出，涵盖从单一构件到项目整体的各层级要素，与国际标准ISO 19650系列中”建成资产（built asset）“的技术内涵一致。施工资源是建设活动过程中投入的生产要素，服务于工程本体的建造，自身不构成永久工程的组成部分。施工材料在不同生命周期阶段具有双重属性：作为待用物资进行采购、运输和存储管理时属于施工资源；经加工安装成为永久工程的组成部分后，其材质和性能信息转化为工程本体构件的属性信息。本标准暂不涵盖劳动力资源的信息建模要求。

### 工程对象应根据项目特征按功能组成和空间组成两种方式进行分解，分解所形成的各级工程对象均应明确其实体对象或逻辑对象的类型归属，并应符合下列规定：
#### 功能分解应以子项、系统、子系统、构件、产品、配件的逻辑功能与组成关系为依据，对实体和逻辑工程对象进行划分。
#### 空间分解应以区域、房间、分区的单一功能为依据，对空间对象及归属于特定空间的实体工程对象进行划分；
#### 功能分解和空间分解可并用，但应保持功能的独立和完整。

> 功能分解和空间分解是工程信息组织中两种互补的分解视角。功能分解沿系统组成的逻辑展开，例如将给水排水系统分解为供水子系统、排水子系统，再细分至水泵、管道、阀门等构件，侧重表达"这些对象共同完成什么功能"。空间分解沿物理区域的边界展开，例如将建筑划分为楼层、防火分区、房间，侧重表达"这些对象位于什么位置"。在实际工程中，两种分解方式往往并用，同一构件既归属于某个功能系统，又定位于某个空间区域。当两者发生冲突时，功能的独立性和完整性优先——例如跨越多个楼层的竖向管井系统不宜按楼层切断，否则会破坏系统的连通性和控制逻辑。

## 信息表述

### 工程信息应按结构化信息和非结构化信息两种方式组织。结构化信息应以数据项为基本单位，非结构化信息应以电子文件为基本单位。

> 结构化信息具有明确的数据类型和字段结构，便于检索、统计、比较和校核；非结构化信息通常以独立文件形式存在，内容格式较为丰富，主要用于阅读、说明和留存。本条区分两种组织方式，并分别明确其基本管理对象，便于后续元数据管理、命名规则和交付控制保持一致。

### 工程对象的信息按表述形式应分为几何信息、文字信息和文档三种类型。其中，几何信息和文字信息属于结构化信息，文档属于非结构化信息。

> 本条从信息表述形式角度对工程对象信息进行分类，目的在于明确不同信息的组织方式和管理对象。其中，几何信息用于表述工程对象的空间形态与位置关系，文字信息用于表述工程对象的属性、参数和说明，文档用于承载不宜拆分为单个数据项的文件化信息。上述分类与 ISO 7817-1 关于几何信息、字母数字信息和文档的划分原则相协调。本标准采用“文字信息”这一表述，以符合国内工程建设标准用语习惯。应当注意，本条所称“表述形式”是指信息在模型和数据环境中的组织与表达方式，并非电子文件格式的分类。

### 几何信息、文字信息应由信息模型承载，文档应通过引用方式与信息模型挂接。

> 本条明确了信息模型在工程信息组织中的核心承载作用。几何信息和文字信息直接存储于信息模型中，有利于保持数据的一致性和可计算性；文档内容形式多样、篇幅不一，更适宜作为独立电子文件管理，并通过统一资源标识符（URI）等方式与信息模型建立稳定关联，以兼顾模型轻量化和信息完整性。

### 几何信息应通过几何元素及其拓扑关系、纹理和光影等表述工程对象的几何呈现形式。

> ISO 7817-1 将几何信息划分为几何细节、几何维度、工程对象方位、外观和参数化驱动形式等要素，各要素的技术含义可参考下表：

<!-- @col-widths: 20, 40 -->
| 几何信息要素 | 技术含义 |
| :---: | :--- |
| 几何细节 | 描述工程对象外轮廓、内部构造、细部构造的几何精细程度 |
| 几何维度 | 描述表达工程对象所采用的几何空间维度特征，如零维（点）、一维（线）、二维（面）、三维（体）或其组合 |
| 工程对象方位 | 描述工程对象的相对或绝对位置、朝向以及坐标信息 |
| 外观 | 描述用于视觉呈现的表面特征信息，如颜色、材质、纹理和光影效果等 |
| 参数化几何驱动形式 | 描述构建和控制几何形态变化的参数化规则与驱动变量 |

### 文字信息应以文字、数字、符号表达工程定义数据集中的项目通用数据、身份标识数据、属性数据和工程关系数据。

> 文字信息是模型单元除几何形体之外最主要的信息载体，主要用于说明工程对象“是什么、具有什么特征、与哪些对象相关”等内容。项目通用数据提供项目层面的基础背景信息；身份标识数据用于实现工程对象的唯一识别和分类定位；属性数据记录工程对象的技术参数和性能指标；工程关系数据描述工程对象之间的组成、连接和控制等逻辑关联。这四类文字信息共同构成工程定义数据集中结构化信息的重要部分。

### 文字信息应以结构化数据项的形式存储和表述，每个数据项应包含标识名称与其对应的取值。各项数据应能通过其标识名称被独立检索和提取，不应将多项独立的信息合并为一段连续的文字描述。

> 本条强调文字信息应采用便于管理和应用的结构化方式进行组织。每项信息均应具有明确名称和对应取值，以便于软件系统进行检索、统计、比对和校核。若将多项独立信息混合写成连续描述，不仅不利于数据交换，也会增加后续整理、复用和自动校核的难度。

### 文档应以电子文件整体形式补充工程信息，文档中局部内容可被提取并转换为几何信息或文字信息。

> 文档主要用于承载不宜拆分为独立数据项的说明性、证明性和记录性信息，如设计说明、计算书、检测报告、影像资料等。随着工程应用深化，部分文档内容可根据实际需要转化为几何信息或文字信息，以支持进一步的结构化管理和应用。

# 工程定义数据集

## 一般规定

### 各级工程对象均应根据信息需求使用模型单元进行数字化表述，形成工程定义数据集。

> 本条强调，工程定义数据集应首先围绕工程对象建立，并以模型单元作为数字化表述的基本载体。工程图纸、技术文档、多媒体等成果，通常是在工程定义数据集基础上按特定信息需求提取、组合或转换形成的表达成果，而不宜直接作为工程定义数据集本体。这样处理，有利于保持工程对象定义的统一性和稳定性，并为后续不同阶段、不同用途的成果表达提供一致的数据来源。点云扫描文件可作为工程对象数字化表述的补充信息来源。

### 工程定义数据集应由项目通用数据、工程对象数据和工程关系数据组成，并应符合表4.1.3的规定。

表: 表4.1.3 工程定义数据集的组成

<!-- @col-widths: 18, 18, 64 -->
| 组成项 | 子项 | 技术含义 |
| :---: | :---: | :--- |
| 项目通用数据 | — | 描述并反映项目全局环境、基础规则与时空定位的数据 |
|  | 项目属性 | 描述项目整体技术与管理特征的文字属性，包含项目标识、建设阶段、参与方信息、区位环境、建筑类别与等级、技术经济指标、性能说明及计量单位体系 |
|  | 项目时空参照 | 定义工程全局或单体局部的基础时空参照框架，包含坐标系统与方位、高程基准、标高体系、界址点、定位轴线及时间基准 |
| 工程对象数据 | — | 描述项目中所包含的实体对象和逻辑对象特征的数据 |

|  | 几何呈现形式 | 描述工程对象空间位置与三维形态特征的结构化几何数据 |
|  | 属性数据 | 描述工程对象固有业务属性及技术参数的结构化文字数据 |

|  | 组成关系 | 系统、子系统、构件或设备、配件之间，上层组合对象与下层组成对象之间的隶属关系 |
|  | 连接关系 | 工程对象之间通过物理接口直接接合的关系 |
|  | 控制关系 | 工程对象之间通过指令、联锁或信号实现驱动与响应的作用关系 |

### 工程定义数据集中，各级工程对象及其信息均应按照现行国家标准《建筑信息模型分类和编码标准》GB/T 51269的有关规定进行分类和编码。当项目需要采用其他分类体系时，应明确标识分类体系来源，并确保各体系之间不产生冲突。

> 在工程实践中，不同行业领域、不同业主方或不同软件平台可能采用各自的分类编码体系。例如，铁路、公路、水利等行业有各自的工程分类标准；部分国际项目要求采用 OmniClass 或 UniClass 等国际通行分类体系；某些业主方或运维平台有内部资产编码规则。本条以 GB/T 51269 为默认分类基准，同时允许项目根据实际需要引入其他分类体系，但要求明确标识来源以便追溯，并在多体系并存时确保同一工程对象在不同体系中的归类不产生语义矛盾。

### 工程定义数据集在通用数据环境中的存储应符合现行国家标准《建筑信息模型存储标准》GB/T 51447的有关规定。

> 工程定义数据集既包含结构化信息（以数据项为最小单位），也包含非结构化信息（以电子文件为最小单位），二者共同构成对工程对象的完整定义。

### 工程用例数据集中，模型单元应在工程定义数据集的基础上按信息需求和工作分解结构重新组织和划分，但不应更改或覆盖工程定义数据集中的原始层级划分数据。

> 工程用例数据集面向具体应用场景形成，可根据特定信息需求和工作分解结构对模型单元进行重新组织和划分。本条强调，这种重组应建立在工程定义数据集基础上进行，不应改变或覆盖其中对工程对象的原始定义和层级关系，以保证基础数据的稳定性和可追溯性。

### 质量验收用例数据集的模型单元按分部分项工程划分时，应符合现行国家标准《建筑与市政工程施工质量控制通用规范》GB 55032的有关规定。

> 施工阶段的质量验收体系是我国工程建设管理的法定要求。本条引用的 GB 55032《建筑与市政工程施工质量控制通用规范》规定了“分部-分项-检验批”的层级组织方式，这是一种面向施工实施和质量管理的过程视角。质量验收用例数据集采用这一划分方式，有利于将数字化信息与现场质量验收活动对应起来，满足施工监管、过程记录和质量追溯的实际需要。

### 竣工移交时，应同时交付工程定义数据集和质量验收用例数据集；运营与维护阶段用例数据集应在工程定义数据集的基础上，按运营与维护阶段信息需求进行重组和划分。

> 竣工移交并不仅是成果汇总节点，也是建设阶段信息向运营与维护阶段延续的衔接节点。本条要求同时交付工程定义数据集和质量验收用例数据集，目的是在移交时既保留对工程对象本体的稳定定义，也保留施工过程形成的质量记录。进入运营与维护阶段后，相关用例数据集仍应以工程定义数据集为基础，按实际应用需求进行重组和调用，以保持基础定义稳定并支持后续持续应用。

## 信息模型架构

### 信息模型应由模型单元组成，交付全过程应以模型单元作为基本操作对象。

> 模型单元是信息模型中承载工程对象数据的基本载体。将模型单元作为交付全过程的基本操作对象，有利于在信息组织、信息生产、成果整合和交付验收等环节保持对象边界一致，从而提高信息的一致性、可追溯性和可复用性。

### 应根据所对应工程对象的层级和作用，将模型单元划分为项目级、功能级、构件级和零件级，各层级均可嵌套设置。

表: 模型单元分级及用途

<!-- @col-widths: 40, 60 -->
| 模型单元分级   | 模型单元用途                                   |
|----------------|------------------------------------------------|
| 项目级模型单元 | 承载项目或子项的全局环境与基础规则的通用信息                |
| 功能级模型单元 | 承载完整功能的模块或空间信息                   |
| 构件级模型单元 | 承载单一的构配件或产品信息                     |
| 零件级模型单元 | 承载从属于构配件或产品的组成零件或安装零件信息 |

> 模型单元的四级分级体系旨在建立一套可兼容多阶段、多专业交付需求的空间与功能逻辑框架。项目级模型单元侧重于项目整体意图、子项目边界或宏观布局的表达。功能级模型单元通过对系列构配件或产品的数字化封装，实现了对物理空间中具备特定功能属性的建筑模块（如工业化集成单元、特殊功能用房）的整体描述。构件级模型单元是建筑信息模型中最基本的操作对象，对应于可独立识别与交付的物理构配件或定型产品。零件级模型单元则针对更深层次的制造加工或安装需求，提供微观层面的组件支撑。模型单元的演进过程反映了工程信息由概略到详尽、由嵌套组合到原子解构的动态深化规律；各层级模型单元通过在模型架构中的逻辑关联，共同构建起支撑建成资产全生命周期管理的数字化内核。

### 信息模型的分解应以项目中对工程对象的层级划分和归属关系为依据，模型单元应与工程对象一一对应。

### 建筑工程中常见系统的模型单元层级划分应符合本标准附录A的有关规定。

> 本条强调，信息模型的分解不应脱离工程对象本身的组成逻辑和归属关系。模型单元与工程对象保持一一对应，有利于在不同阶段、不同参与方和不同应用场景之间保持语义一致，减少因模型拆分方式随意变化而造成的信息割裂和重复映射。

### 信息模型精细度可用于评估信息模型的表述能力，并宜按最小模型单元的层级确定。根据工程项目的信息需求，可在基本等级之间扩充模型精细度等级。

表: 模型精细度基本等级划分

<!-- @col-widths: 20, 50, 10, 20 -->
| 等级            | 英文名                        | 代号   | 包含的最小模型单元 |
|-----------------|-------------------------------|--------|--------------------|
| 1.0级模型精细度 | Level of Model Definition 1.0 | LOD1.0 | 项目级模型单元     |
| 2.0级模型精细度 | Level of Model Definition 2.0 | LOD2.0 | 功能级模型单元     |
| 3.0级模型精细度 | Level of Model Definition 3.0 | LOD3.0 | 构件级模型单元     |
| 4.0级模型精细度 | Level of Model Definition 4.0 | LOD4.0 | 零件级模型单元     |

> 工程实践中对“模型精细度”（简称为 LOD）的内涵往往存在理解差异。由于该概念缺乏统一且可量化的考核指标，若在合同条款中单纯使用“模型精细度”界定交付成果，易因表述模糊引发履约争议，因此本标准不建议将其作为唯一的交付约束条件。然而，鉴于“模型精细度”已被行业广泛认知并形成普遍观念，本标准保留了该术语以辅助交流，但在具体应用层面弱化了其强制约束力。此外，本标准对模型精细度的英文取义采用了“Level of Model Definition”，未直接引入特定机构的“Level of Development”（也简称为 LOD）体系及其细分层级（如 LOD 100～500），以避免不必要的版权风险。

## 项目通用数据

### 项目通用数据应描述工程项目整体层面的基础信息、通用规则和共用约束。

> 本条说明项目通用数据的性质。项目通用数据不针对某一单独工程对象，而用于支撑全部工程对象的数字化表述、识别、组合和应用，是工程定义数据集中的全局性基础数据。

### 项目通用数据应由项目级模型单元统一承载，其他各级模型单元应通过继承方式共享项目通用数据，不应重复定义。

> 项目通用数据不依附于物理实体构件，而是为整个工程模型提供全局性的基准数据。将其统一由项目级模型单元承载并允许下级单元继承，可避免信息在各个构件中重复录入，进而保障全局数据的一致性。

### 项目通用数据应分为项目属性和项目时空参照两类，并应包括下列信息：
#### 项目属性应包括项目标识信息、工程建设阶段、建设参与方信息、建设区位与环境、建筑类别与等级、技术经济指标、性能说明和计量单位体系；
#### 项目时空参照应包括坐标系统与方位、高程基准、标高体系、界址点、定位轴线和时间基准。

> 各类项目通用数据的内容示例见下表。

表: 项目通用数据内容示例

<!-- @col-widths: 20, 80 -->
| 信息分类 | 内容示例 |
| :---: | :--- |
| 项目标识信息 | 项目名称、项目编号、项目简称 |
| 工程建设阶段 | 项目所处阶段标识 |
| 建设参与方信息 | 建设单位、勘察单位、设计单位、施工单位、监理单位的名称、资质、联系方式 |
| 建设区位与环境 | 项目地点、地理坐标、气象气候与自然条件 |
| 建筑类别与等级 | 建筑类别、结构类型、设计使用年限、耐火等级、抗震设防标准 |
| 技术经济指标 | 总用地面积、总建筑面积、容积率、建筑密度、绿地率、总投资 |
| 性能说明 | 结构性能、防火性能、节能性能、绿色建筑等级 |
| 计量单位体系 | 项目采用的计量单位、量纲及精度规则 |
| 坐标系统与方位 | 坐标系名称、项目基点、测量点、真北偏转角 |
| 高程基准 | 高程基准名称 |
| 标高体系 | 标高名称、标高值、水平参照面 |
| 界址点 | 界址点编号、坐标值 |
| 定位轴线 | 轴号、轴线参照面 |
| 时间基准 | 所在时区、时间基准 |

### 工程对象数据应根据信息需求，采用几何信息表述工程对象的形态、尺寸、位置、朝向和空间占位，采用文字信息表述工程对象的身份标识、属性和关系，采用文档表述不宜直接结构化表达或需保持原件形态的信息，并应建立各类信息之间的关联关系。

> 本条承接前文关于几何信息、文字信息和文档三种表述形式的规定，说明工程对象数据在交付中的组织方式。工程对象的完整表述通常需要根据具体信息需求，对不同信息形式作适当配置，并通过引用、挂接或数据关联等方式建立联系，以形成可检索、可校核、可传递和可应用的完整信息。

## 身份标识数据

### 身份标识数据应描述工程对象在项目中的身份特征，作为工程对象识别、检索、关联和管理的基础数据。

> 本条说明身份标识数据的性质。身份标识数据用于回答“该对象是谁、属于哪一类、在项目中如何识别”等问题，是工程对象数据建立对应关系、形成引用关系并支撑后续应用的基础。与项目通用数据不同，身份标识数据直接对应具体工程对象及其类型特征。

### 身份标识数据应包括代号、名称、分类编码和描述，并应符合下列规定：
#### 代号应针对工程对象实例编制，并应能够在项目范围内唯一识别工程对象；
#### 名称应针对工程对象实例编制，并应反映工程对象的功能类型、位置信息或其他主要识别特征；
#### 分类编码应针对工程对象类型编制，并应符合国家现行标准《建筑信息模型分类和编码标准》GB/T 51269的有关规定；当项目有特殊需求时，可采用项目自定义的分类体系，但应在交付时声明所采用分类体系；
#### 描述应用于补充说明代号、名称和分类编码无法充分表达的工程对象特征，可省略。

> 本条对身份标识数据的组成和编制层次作出规定。代号和名称主要用于识别项目中的具体对象实例，便于在交付、审核、检索和引用过程中进行人工辨识；分类编码主要用于表明对象所属类别，便于统计、归类、交换和跨项目复用；描述用于补充说明特殊情况。通过区分实例标识与类型标识，可减少同名异物、同物异码等问题，提高工程对象数据的一致性。

### 身份标识数据宜纳入元数据，在通用数据环境中统一管理，与全局唯一标识符（UUID）共同构成完整的标识类元数据。

> 身份标识数据侧重从工程业务角度识别对象，全局唯一标识符（UUID）侧重从数据管理角度保证对象在跨平台、跨阶段流转中的唯一性和可追溯性。将两类标识统一纳入元数据管理，有利于在通用数据环境中同时实现人工检索、系统关联和版本追踪。

## 几何呈现形式

### 几何呈现形式应描述工程对象的形态、尺寸、位置、朝向和空间占位等几何特征。

> 本条说明几何呈现形式的内容范围。几何呈现形式用于反映工程对象在空间中的基本状态，是识别工程对象空间关系、开展布局校核、建造实施和交付应用的重要基础。本标准着重规定几何信息应表达的内容和达到的程度，至于采用三维形体、二维图形或符号等具体表达方式，由相关表达标准作进一步规定。

### 几何呈现形式应根据信息用例的需求确定，在满足需求的前提下应遵循最小必要原则，避免过度建模。

### 涉及几何仿真模拟、视觉效果呈现、空间布局与校核、加工制造或现场浇筑，以及形态无法由二维投影唯一确定的模型单元，其几何信息应采用三维形体表达。

### 需要现场加工或浇筑的工程对象，其几何信息应满足相应生产建造工艺要求，并应表达构造尺寸；可整体采购的定型产品或设备，其几何信息宜以标称尺寸和空间占位为主，具体产品特征宜通过文字信息补充表达。

### 模型单元的空间占位应反映工程对象的物理边界或影响边界，影响边界应包含形变、加工公差及安装维修所需的预留空间。

### 项目级和功能级模型单元的位置和朝向应采用项目工程坐标系表达；构件级和零件级模型单元宜采用局部坐标系表达，并应在项目中放置后由项目工程坐标系唯一确定。

### 具有安装、运输或系统连接需求的模型单元，应在关键界面或关键部位设置定位基点、安装锚点或连接节点，并采用符号明确标识。

### 模型单元的几何信息可采用几何表达精度（Gx）进行分级，几何表达精度的等级划分宜符合表4.3.5的规定。

表: 表 4.3.5 几何表达精度的等级划分

<!-- @col-widths: 20, 20, 10, 50 -->
| 等级 | 英文名 | 代号 | 适用范围 |
| :--- | :--- | :---: | :--- |
| 1级几何表达精度 | level 1 of geometric detail | G1 | 满足二维化或符号化识别需求 |
| 2级几何表达精度 | level 2 of geometric detail | G2 | 满足空间占位、主要颜色等粗略识别需求 |
| 3级几何表达精度 | level 3 of geometric detail | G3 | 满足建造安装流程、采购等精细识别需求 |
| 4级几何表达精度 | level 4 of geometric detail | G4 | 满足高精度渲染展示、产品管理、制造加工准备等需求 |

> 几何表达精度体现了模型单元与物理实体在形态上的逼近程度。例如同一台设备，既能表达为一个简单的占位体甚至一个符号，也能精确描述其外形细节。本标准规定的四个级别与工程阶段不存在一一对应关系，而是由具体的项目信息需求决定。例如方案设计阶段为展示设计效果往往需要 G4 精度，而施工图设计阶段通常采用 G3 精度即能满足需求。
> 在满足信息需求的前提下，优先采用较低的几何表达精度，将更多工程特征以文字信息（属性）的形式表达，有利于避免过度建模、控制模型文件体量和提高运算效率。
> 本标准仅作框架性规定，关于几何表达精度的详细要求参见相关专项标准。

## 属性数据

### 工程对象的属性数据应采用模型单元的文字信息表述工程对象的特征信息，并应以结构化数据项的形式存储。

> 本条说明属性数据的性质。属性数据用于表达工程对象的物理性能、技术参数、材质构造、生产安装、资产运维等几何信息以外的特征，是支撑检索、统计、校核、交换和应用的主要数据形式。采用结构化数据项存储，有利于各项信息被独立识别、提取和复用。

### 属性数据应依据工程对象类型采用数据模板进行定义。同一类型工程对象的属性数据输入、校核和输出，均应依据对应的数据模板。

> 数据模板是约束属性数据结构与内容的核心工具。通过在信息生产前统一确定数据模板，可使同类工程对象在不同专业、不同参与方之间遵循一致的字段定义、数据类型、单位和取值规则，从源头保障数据的一致性和可交换性。数据模板面向具体工程对象类型规定“这类对象需要哪些属性”，不同于面向全局术语管理的数据字典。

### 数据模板的数据项定义宜包含属性组标识、属性组名称、属性标识、属性名称、数据类型、单位符号和取值规则，可包含属性说明、是否必填、对应定义和数据来源等补充字段。

> 数据模板的数据项定义示例见下表：

<!-- @col-widths: 20, 40, 40 -->
| 字段 | 说明 | 示例 |
| :--- | :--- | :--- |
| 属性组标识 | 属性组的分类编码 | ST-200 |
| 属性组名称 | 属性组的中文名称 | 关联关系 |
| 属性标识 | 属性的分类编码 | ST-201 |
| 属性名称 | 属性的中文名称 | 关联模型单元名称 |
| 数据类型 | 属性值的数据类型 | string |
| 单位符号 | 计量单位符号 | — |
| 取值规则 | 对属性值的约束 | 自由文本 |
| 属性说明 | 属性含义的补充说明 | 与本模型单元存在关联关系的其他模型单元名称 |
| 是否必填 | 该属性是否为必填项 | 是 |
| 对应定义 | 对应的数据标准、数据字典或交换模型定义 | IfcRelationship |
| 数据来源 | 属性值的责任方 | DS（设计） |

### 数据模板中属性组和属性的标识及名称应符合下列规定：
#### 标识及名称应在项目范围内保持统一；
#### 属性标识宜采用符合国家现行标准《建筑信息模型分类和编码标准》GB/T 51269规定的分类编码表述，当项目有特殊需求时，也可采用项目自定义的标识体系，但均应在交付时明确声明所用体系的特定标识；
#### 属性名称宜基于所采用分类体系中对应编码的分类名称确定。

### 当数据模板中引用分类编码标准或自定义分类编码方案作为属性标识或取值时，应明确所采用分类体系及其版本，并宜采用下列方式之一进行机器可读表达：
#### 编码宜带有命名空间前缀，前缀应包含分类编码标准或方案的名称，并宜包含版本号或年号；
#### 宜在独立数据项中给出所引用分类编码标准或方案的名称，并宜包含版本号或年号；
#### 宜在独立数据项中给出所引用分类编码标准或方案的统一资源标识符（URI）。

> 明确分类体系及其版本，有利于避免属性标识和取值在交换、解析和长期保存过程中产生歧义。

### 数据模板中属性值的数据类型应符合本标准关于文字信息数据类型的有关规定。

### 数据模板中属性值的单位符号应符合下列规定：
#### 具有量纲的属性值应明确标注计量单位，计量单位及其符号表示应符合国家现行有关标准的规定；
#### 比值类属性值应采用统一的表示方式，百分数数值应注明“%”符号；
#### 无量纲的属性值，应在单位符号字段中填写占位符“—”；
#### 当属性值采用枚举类型时，应预先定义枚举选项集。

### 复合型工程参数应拆分为独立的数据项分别存储，不应合并为连续的组合字符串。范围类属性宜拆分为最小值和最大值分别存储。

### 数据模板的内容应以信息需求为导向，仅包含当前阶段和应用场景所需的属性数据项，不应编制与需求无关的冗余字段。

### 数据模板宜采用计算机可读的结构化格式编制，并宜支持属性数据的自动化校验。

### 数据表应按数据模板填写属性数据后形成，其属性数据应与模型单元中存储的属性值保持一致。

> 数据表是数据模板从“结构定义”转化为“实例数据”的产物，也是属性数据脱离建模软件环境后进行跨系统交换的主要载体。数据表可以按数据模板逐类工程对象编制，也可以按统一格式汇集多类工程对象的属性数据。无论采用何种组织方式，数据表中的属性数据均应以模型单元中的属性值为唯一数据源，确保数据表与信息模型之间不产生偏差。

### 属性数据应作为信息应用的主要依据。当属性值与几何信息的量测值不一致时，应以属性值为准。

### 可采用信息深度（Nx）对模型单元属性信息的丰富程度进行分级，信息深度的等级划分宜符合表4.3.7的规定。

### 常见模型单元属性数据层级应符合本标准附录B的有关规定。

表: 表 4.3.7 信息深度等级的划分

<!-- @col-widths: 20, 30, 10, 40 -->
| 等级 | 英文名 | 代号 | 描述范围 |
| :---: | :---: | :---: | :--- |
| 1级信息深度 | level 1 of information detail | N1 | 身份描述、项目信息、组织角色等基本信息 |
| 2级信息深度 | level 2 of information detail | N2 | 在N1基础上增加系统关系、组成及材质、性能等信息 |
| 3级信息深度 | level 3 of information detail | N3 | 在N2基础上增加生产信息、安装信息 |
| 4级信息深度 | level 4 of information detail | N4 | 在N3基础上增加资产信息和维护信息 |

> 信息深度等级（Nx）提供了一种对属性信息丰富程度的概略性描述，便于在项目早期各参与方就信息交付范围形成初步共识。但由于各级别的边界较为笼统，难以作为合同履约的精确考核依据，在实际应用中，具体的属性交付内容仍需依据项目约定的信息需求和数据模板逐项明确。本标准保留该分级体系，主要考虑到行业对这类概念已有较广泛认知，Nx 作为沟通工具有助于降低交流成本。

## 工程关系数据

### 工程关系数据应描述工程对象之间的工程逻辑关系，并应包括空间关系、组成关系、连接关系和控制关系。

> 本条说明工程关系数据的性质。工程关系数据用于表达工程对象之间在空间、系统、构成和控制方面的关联，使工程对象数据形成具有内在逻辑的信息整体，而非彼此孤立的数据集合。模型单元与图纸、文档、分类编码或外部数据资源之间的引用关系，属于交付成果层面的索引机制，可在有关交付成果的章节中另行规定。

### 工程关系数据应符合下列规定：
#### 空间关系应表明工程对象与所在场地、区域、空间或其他空间单元之间的归属关系；
#### 组成关系应表明工程对象与其直接上层对象之间的隶属关系；
#### 连接关系应表明具有物理接口的工程对象之间的直接连接关系；
#### 控制关系应表明控制对象与被控制对象之间的直接控制、联锁或信号作用关系。

> 本条从工程应用角度规定四类基本关系。空间关系用于明确对象所在位置或所归属空间；组成关系用于表达系统、部件、构件之间的上下层级；连接关系用于表达对象之间的物理连接或接口关系；控制关系用于表达运行逻辑中的控制与被控制关系。不同工程领域可根据实际信息需求，对各类关系作进一步细化。

### 每条工程关系记录至少应包括下列内容：
#### 关系标识；
#### 源对象标识；
#### 关系类型；
#### 目标对象标识。

> 本条规定工程关系记录的基本构成。关系标识用于区分不同关系记录；源对象标识和目标对象标识用于明确关系两端所对应的工程对象；关系类型用于表明该记录属于空间关系、组成关系、连接关系或控制关系中的何种关系。工程关系在实际应用中可呈现一个对象对应一个对象、一个对象对应多个对象或多个对象对应一个对象等情形。对需表达方向、接口、状态或时效的关系，可根据需要增加相应补充数据项。

> 工程关系记录示例见下表：

<!-- @col-widths: 20, 20, 20, 20, 20 -->
| 关系标识 | 源对象标识 | 关系类型 | 目标对象标识 | 补充数据项示例 |
| :--- | :--- | :--- | :--- | :--- |
| GX-001 | 构件-001 | 空间关系 | 空间单元-01 | 所属区段 |
| XT-001 | 系统-01 | 组成关系 | 子系统-01 | 上下层级顺序 |
| SB-001 | 设备-01 | 连接关系 | 管线-01 | 接口编号、流向 |
| KZ-001 | 控制器-01 | 控制关系 | 设备-02 | 控制方式、生效状态 |

### 工程关系数据应以结构化数据项为基础进行存储；连接关系和控制关系在有需要时，可结合几何呈现形式或图示进行表达，其表达结果应与结构化关系数据保持一致，并应满足检索、校核、交换和应用的需要。

> 结构化数据项是工程关系数据进行检索、统计、交换和自动化校核的基础。对于连接关系和控制关系，仅以文字字段记录往往不足以满足空间识别、接口辨认和系统逻辑表达的需要，因此可结合三维几何连通性、系统原理图或控制逻辑图等形式进行表达。但无论采用何种表达方式，均应以结构化关系数据为依据，并保持内容一致，以避免图示、几何表现与关系数据脱节。

### 工程关系数据的数据类型应符合本标准关于文字信息数据类型的有关规定。

# 元数据

## 一般规定

### 元数据规则应由项目统一制定，用于描述数据项和电子文件的标识、状态、来源、权限等管理特征，并宜包括数据管理、流程管理和组织管理三个类别。

> 元数据是工程信息得以识别、检索、流转和追溯的基础。工程信息不仅需要表达“内容是什么”，还需要明确“由谁形成、处于何种状态、能否使用、如何管理”。本章所规定的元数据，主要面向数据项和电子文件在通用数据环境中的管理需要，不替代工程对象本身的几何信息、属性数据和工程关系数据。

### 元数据项的数据类型应符合本标准关于文字信息数据类型的有关规定。

### 数据管理类的元数据项应主要用于表述数据项和电子文件的标识及技术状态，并宜符合下表的规定：

表: 数据管理元数据

| 元数据项 | 数据类型 | 赋值规则 |

### 数据项和电子文件应通过元数据标记流转状态，并在工作中、共享、提交、出版或存档等状态中进行流转，且应符合下列规定： {#workflow-state}
#### 工作中（WIP）状态的数据不应用于正式交付或正式业务；
#### 共享（SHARED）状态的数据可被指定的参与方用于协同和信息交换；
#### 提交（SUBMITTED）状态的数据可被指定的参与方用于审核；
#### 出版（PUBLISHED）状态的数据可作为正式的交付成果或基准，供指定的参与方使用；
#### 存档（ARCHIVED）状态的数据可作为历史记录及最终交付成果，供指定的参与方查阅。

> 流转状态是元数据中最核心的管理属性之一，决定了数据在协同流程中的可用范围和信任等级。五种状态对应了数据从产生到归档的完整生命周期：工作中的数据仅供责任方内部使用，不具备对外效力；共享后其他参与方可将其作为协同依据；提交后进入正式审核流程；出版后正式纳入交付成果；存档后作为项目历史记录长期保存。状态的流转通常伴随审核动作，即流程管理类元数据（审核者、审核日期、审核结果）的同步更新。
> 本条所称“流转状态”，对应 `ISO 19650-2` 中的信息容器 `state`。该草案中的 `status` 主要用于表示信息适用性，或表示信息已经获得授权和接受，含义与本条所述流转状态不同。

## 命名规则

### 数据项和电子文件的命名应依据其所属元数据字段按规则组合形成，并应保持简明且易于辨识。

### 同一项目内数据项和电子文件的命名规则及版本标识规则应保持全局一致，且不应重复或冲突。当发生变更时，应按照规定流程进行版本升版与发布。

> 科学的命名有利于数据项与电子文件的识别、检索和机器处理，对于协同工作极为重要。这本质上是将关键的元数据项（如项目编号、责任方、阶段、专业、分区等）显性化为文件或对象名称的过程。通过基于元数据的组合命名，可确保命名系统与数字资产管理属性的一致性。本章条文为通用性的命名组合提供基本框架，具体字段的选用及组合逻辑通常由项目基于其管理特征确立。

### 命名格式应简明且易于辨识，宜符合下列规定：
#### 宜使用汉字、英文字符、数字、半角下划线“_”和半角连字符“-”的组合；
#### 字段内部组合宜使用半角连字符“-”， 字段之间宜使用半角下划线“_”分隔；
#### 各字符之间、符号之间、字符与符号之间均不宜留空格；
#### 不应使用文件系统保留字符。

> 对象和参数命名层面对中英文字符、符号的选用存在不同的实践惯例。由于部分软件对中文命名敏感或存在识别差异，国内工程实践中通常采用符合受众习惯的中文，或广为接受的专业缩写（如以“C20”表示混凝土强度等级，而不使用全拼写“concrete”）。在各字段之间使用种类统一、数量有限的分隔符号（例如仅使用半角下划线和半角连字符），有助于防止命名格式混乱，并利于计算机程序解析。

### 电子文件夹的名称宜由顺序码和描述依次组成，并宜符合下列规定：
#### 顺序码宜采用文件夹管理的编码，可自定义；
#### 内容标识可自定义，表述项目简称、工程阶段、文件夹类型等信息。

> 科学、清晰的文件夹组织与命名有利于项目参与方之间的协同交流与信息检索。本条规定的“顺序码+描述（内容标识）”为通用性的基础架构，旨在保障基本资料组织秩序的前提下，赋予项目执行团队充分的灵活性，以适应复杂的工程实际情况及不同参建单位的IT习惯。
> 在具体工程实践中，建议基于此基础架构在项目信息生产计划或项目信息标准中按需细部约定。例如，可参考国际主流通用数据环境（CDE）的协同管理思路，在实际创建工作文件夹时，将项目简称、工程阶段，以及文件所处的技术状态（如表示审批与流转状态的“工作中（WIP）”“共享”“提交”“出版交付”“存档”，以及“外部参考数据”“资源库”等专门管理类型）按序纳入标识字段中，从而形成具有可操作性的协同管理基准。

### 电子文件的名称应基于核心元数据字段组合形成，宜由项目标识、阶段标识、空间或系统标识、专业标识、顺序号、版本标识和描述依次组成，并宜符合下列规定：
#### 项目标识宜对应项目编号、项目代号或项目简称，采用项目统一定义的缩写或编码；
#### 阶段标识宜简述文件所属的工程阶段或项目级预设用途（如方案设计、施工图设计、竣工图等）；
#### 空间或系统标识应简述物理空间分区、工程区段、单位工程、分部工程或逻辑系统，可使用工程代号或中文简称；
#### 专业标识宜符合本标准附录C的有关规定，可采用其中的专业代码或简称；当涉及多专业融合模型时，可并列标注或统称为“综合”；
#### 顺序号宜由固定位数的数字组成，用于同一空间、同一专业下的文件排列序号（如图号、模型分区编号等）；
#### 版本标识的格式宜符合本标准元数据中版本标识的规定；
#### 描述信息为非必选项，可自定义，用于补充说明文件类型的具体特征。

> 电子文件命名可协助快速识别文件内容，对于多参与方协同和长期管理具有重要意义。不同工程项目可基于自身业务特点确定字段组合顺序，但同一项目内应保持统一。考虑到工程类型、交付载体和管理方式存在差异，本条仅规定命名字段的基本构成与组合原则，不对具体组合方案作唯一限定。

# 交付准备

## 一般规定

## 信息需求

### 信息生产和交付前应识别信息需求，并形成信息生产要求文件，作为信息生产和交付的依据。

### 信息需求应综合体现建筑信息模型交付的目标、范围和条件，并应包含下列内容：
#### 应评估行政管理部门、项目建设单位和参建单位对信息的需求；
#### 应根据工程建设过程中的质量、进度和成本管理要求，分阶段提出项目信息用例；
#### 宜考虑资产运营、维护和管理等方面对信息的需求。

### 信息生产要求文件应完整描述信息交付的背景、方式和规则，并应包含下列内容：
#### 项目信息应用背景、目标和基本原则；
#### 信息交付范围和交付关键节点；
#### 信息模型架构、拆分和整合规划；
#### 各参与方的组织架构和职责、交付程序；
#### 信息用例清单，各用例所需的几何信息、文字信息和文档的需求；
#### 交付成果清单、交付载体和数据格式；
#### 交付成果的元数据；
#### 执行的标准规则，必要时可另行成文；
#### 通用数据环境和各信息生产方的信息技术环境要求；
#### 质量控制与验收要求；
#### 风险防范和保障措施；
#### 知识产权方面的约定。

## 数据资源

### 应根据项目要求和信息需求，对各类数据资源进行收集、识别和整理，并应对其有效性、准确性和格式兼容性进行复核。

> 作为交付准备的重要环节，清晰、可靠的数据资源是保障后续信息生产准确性的根基。实践中，大量返工来源于上游设计变更未及时分发，或是现状测绘数据与信息模型的原点基础不一致。因此，本环节除了“收集”，更强调“复核”。

### 数据资源应作为信息生产和交付的输入条件，内容宜包括下列类型：
#### 现状基底数据，包括地形地貌、地质勘察、气候环境以及现有工程资产数据等；
#### 前序移交成果，包括前一工程阶段交付的信息模型、工程图纸和相关技术文档等；
#### 技术约束条件，包括适用的标准规范、技术准则、数据字典、数据模板、构件库、产品库、样式库等；
#### 项目管理规则，包括项目组织架构、协同工作流程、协同平台权限划分及其他项目管理数据等。

### 应依据工程对象分解结构，为各类实体对象和逻辑对象配置标准化的数据模板，以约束后续信息生产中属性数据的结构与内容。数据模板应在信息生产前发布。

### 数据模板在项目实施过程中发生变更时，应记录变更内容和版本，已生产的属性数据应按变更后的数据模板进行核查。

### 对非结构化的数据资源，宜提取其中的约束性参数和关键指标，转换为计算机可读的结构化数据。
> “结构化转换”是指将传统的纸质任务书、自然语言的规范要求，提前梳理为参数列表或数据字典，以便在后续信息建立时直接作为属性字段进行映射和挂接，从而提高信息生产效率。

### 数据资源应在通用数据环境中的指定区域集中管理与共享，明确标识其版本及流转状态，并制定相应的数据更新机制。

# 信息生产和交付

## 一般规定

### 信息生产前，应依据本标准关于工程对象分解结构的规定进行生产任务分解，并应符合下列规定：
#### 生产任务的划分应保持工程对象功能逻辑与空间逻辑的完整性；
#### 应确定各分支生产任务的输入条件、输出交付成果及相应的验收标准；
#### 应明确不同生产任务之间的前置依赖关系及协同交互节点。

### 应根据信息生产要求制定相应的信息生产计划，并依据该文档进行组织和实施。

### 应制定组织架构和责任矩阵表，规定信息生产和交付过程中各参与方的职能和参与人员的责任，并宜符合下列规定：
#### 宜包括建设、设计、施工、监理、产品制造、全过程咨询等工程职能；
#### 宜明确信息模型咨询、信息应用等专项职能；
#### 可按工程合约形式标记总承包单位、分包单位；
#### 必要时，可列出行政审批单位，运营单位或设施管理单位；
#### 当设计、施工单位同时承担信息模型咨询职能时，宜将工程职能和信息模型职能分开列出。

> 本条中的信息模型咨询单位，是指与项目建设单位建立信息模型专项咨询合约的承担单位，提供独立于设计或施工的专业咨询服务，既可能与项目设计或施工单位为同一单位，也可能是第三方咨询单位。

### 信息生产应以建立和维护模型单元为主要方式，模型视图、明细表、数据表和技术文档可作为辅助表达方式。

### 信息生产过程中，应按照本标准第4章的有关规定，对收集和生成的各类信息进行组织。

### 模型单元应依据工程定义整合形成信息模型，整合过程应符合下列规定：

#### 具有组成关系的模型单元，应按系统层级进行嵌套整合；
#### 具有空间归属关系的模型单元，应按空间层级进行定位整合；
#### 具有相同分类属性的模型单元，应按分类体系进行归集整合。

### 根据信息用例需求，可对模型单元进行专项整合，且应保持信息模型的逻辑关系的完整性。

> 信息模型的分解是实现“单元化生产、协同化整合”的基础。功能分解侧重于功能关联（如消防水系统的连通性），空间分解侧重于空间位置。当功能分解和空间分解并用时，保持功能的独立性和完整性相对重要。例如，桥梁往往分为上部空间和下部空间，这对于结构构件的划分是合理的，但是对于机电系统，这样划分可能会导致部分子系统（例如供电系统）被切割。在这种情况下，较为适宜的做法是机电系统不跟随空间划分，而依据功能组成独立划分。再如，机场建设项目可划分为飞行区和航站区等。航站区内部的机电系统相对独立性较强，此时可先分解为区域，再在区域内部进行功能分解。
> 例如，在本体信息模型中，钢筋信息分散存储于柱、梁、板、墙等多个构件中；而钢筋工程管理需要将这些钢筋信息按分部工程维度聚合，形成统一的钢筋业务信息模型，用于材料统计、进度管理和成本控制。

### 信息生产过程中应捕获和维护数据项和电子文件的元数据。

### 信息生产可在各参与方的企业数据环境或通用数据环境中完成，但跨组织共享信息应在通用数据环境中完成。

### 信息生产过程中，数据项和电子文件的流转状态应符合下列规定：
#### 正在编制的数据应标记为工作中（WIP）状态；
#### 经信息提供方内部检查合格的数据，应转为共享（SHARED）状态后方可供协同各方使用；
#### 已出版（PUBLISHED）的数据需要修改时，应创建新版本，新版本应从工作中（WIP）状态重新流转。

> 在信息生产阶段，流转状态的核心作用是区分“仍在编制中的草稿”与“可供他方引用的协同数据”。工作中状态保护了未成熟数据不被误用；共享状态标志着数据已通过内部质量检查，可以作为协同依据。对已出版数据的修改必须创建新版本并从工作中状态重新流转，以确保已发布的基线不被篡改。

## 信息交付

### 应根据信息需求，从信息生产成果中收集和整理各级模型单元、模型视图、明细表、数据表、技术文档等内容，按交付要求进行整合。

### 信息交付成果的呈现形式包括信息模型、工程图纸、数据表、技术文档和多媒体，其中信息模型、工程图纸和数据表为主要形式，技术文档和多媒体为辅助形式。

### 信息模型应按本标准第4.4节的规定，依据工程对象分解结构对模型单元进行整合。

### 模型视图中显示的注释和明细表，应从所关联模型单元的属性数据中提取，不应脱离模型单元独立存储或重复录入属性值。

### 工程图纸应在模型视图、明细表和数据表基础上增加制图要素生成。

### 工程图纸、技术文档和多媒体中包含模型单元无法直接承载的信息时，应作为关联文档或外部引用文件与对应的模型单元建立关联关系。

> 文档是工程对象信息的非结构化载体，包括技术文档、工程图纸和多媒体文件等。本标准将文档定位为独立于工程对象数据之外的一种信息表述形式，不作为工程对象数据的组成子项。文档所承载的信息在需要结构化管理时，应提取为模型单元的属性数据；文档本身则通过引用关系与模型单元保持关联。

### 关联文档应具有在项目范围内唯一的统一资源标识符（URI），且在约定的信息生命周期内应保持该标识符的可用性与指向的准确性。

### 关联文档与模型单元之间应建立稳定的链接引用关系，并应通过下列方式之一实现：
#### 将关联文档的统一资源标识符（URI）作为模型单元的属性值存储；
#### 在通用数据环境中通过元数据建立文档与模型单元的映射关系。

### 技术文档应包括全部被模型单元引用的关联文档。明细表和数据表可作为技术文档的组成部分，也可作为独立交付成果。

### 关联文档宜采用符合相关国家标准的公开格式存储。

### 链接引用关系应保持有效。当关联文档发生变更时，应及时更新模型单元中的引用信息。

### 工程图纸和技术文档中的信息与模型单元中的信息可重合，但不应冲突；当发生不一致时，应以模型单元中的信息为准。

### 多媒体以影像、声音、三维扫描等形式记录的工程实体信息，可独立交付，也可作为外部引用文件与对应的模型单元建立关联关系。

### 交付成果的电子文件格式应符合现行国家标准和行业标准的规定，宜同时提供信息生产软件的原生格式文件。

### 交付成果经信息提供方整理完成后，应在通用数据环境中转为提交（SUBMITTED）状态，并提请信息需求方进行审核。

### 应根据信息生产要求文件对提交状态的交付成果进行检测和审核，使交付成果满足本标准第3.0.1条的要求，并应符合下列规定：
#### 审核通过的交付成果应转为出版（PUBLISHED）状态，完成正式交付；
#### 审核结果为拒绝或退回的交付成果应回退为新版本的工作中（WIP）状态，由信息提供方修改后重新流转；
#### 项目结束或阶段归档时，出版状态的交付成果可转为存档（ARCHIVED）状态。

### 流转状态的每次转换均应在通用数据环境中记录，并同步更新审核者、审核日期、审核结果等流程管理类元数据。

### 交付成果的表达方法应符合《建筑信息模型表达标准》的有关规定。

### 信息交付成果移交时，应编制成果移交说明文件，并随同交付成果一并移交。

### 成果移交说明文件应帮助接收方快速了解本次移交成果的整体内容和组织方式，并应包含下列内容：
#### 概述信息，包括项目信息、移交范围、移交日期、交付方与接收方责任人信息及移交内容简述；
#### 成果清单，包括成果总体统计、各类成果的目录索引位置及用途说明；
#### 组织规则说明，包括文件夹结构概述、命名规则要点、分类编码体系简介及数据模板类型说明；
#### 使用指南，包括目录浏览和文件查找方法、推荐软件清单及技术支持联系方式。

> 成果移交说明文件的定位是总体说明文档，而非交付成果本身。在大型工程项目中，信息交付成果涉及的模型、图纸、文档数量庞大且组织关系复杂，接收方往往难以在短时间内理解成果的全貌。一份结构化的移交说明能够显著降低接收方的学习成本，也有利于后续运维阶段的数据检索与利用。

# 本标准用词说明

1 为便于在执行本标准条文时区别对待，对于要求严格程度不同的用词说明如下：

- 表示很严格，非这样做不可的：
- 正面词采用“必须”；反面词采用“严禁”；
- 表示严格，在正常情况下均应这样做的：
- 正面词采用“应”；反面词采用“不应”或“不得”；
- 表示允许稍有选择，在条件许可时首先应这样做的：
- 正面词采用“宜”；反面词采用“不宜”；
- 表示有选择，在一定条件下可以这样做的，采用“可”。

2 条文中指明应按其他有关标准执行的写法为“应按......执行”或“应符合......的规定”。
