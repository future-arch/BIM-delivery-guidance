# 第九章：运营维护阶段交付与应用 (O&M Stage)

> **本章导读**
>
> 运营维护阶段是 BIM 交付链中持续时间最长的阶段，从竣工移交至建筑物拆除可能跨越数十年。这一阶段的核心命题与设计、施工、移交三阶段有本质差异：前三阶段是"项目（Project）"逻辑，目标是把建筑造出来并交付出去；运维阶段是"运营（Operations）"逻辑，目标是让建筑在长期使用中持续创造价值。BIM 数据在运维阶段从"交付物"转变为"运营基础设施"，被运维方持续消费、修订、扩展，并在合适的节点（重大改造、产权变更、最终拆除）回归为新的项目阶段输入。
>
> 本章承接第八章竣工移交阶段的数字资产，按"阶段定位 → 信息需求与典型应用 → 关键技术与方法 → 实施步骤与角色责任 → 中国工程语境的特殊约束 → 常见失败模式"的脉络展开。运维阶段在中国有强制性的物业管理、特种设备管理、能耗监测要求，物业管理条例、特种设备安全法、能源管理体系等法规对 BIM 数据的存活、更新、应用提出了明确的本地约束。本章在通用方法之外专门梳理这些本地约束，并落到运维 BIM 工作人员可以照做的工具与流程层面。

## 9.1 阶段定位与交付价值

### 9.1.1 运维阶段在生命周期中的位置

运维阶段是国家工程建设程序中"使用阶段"的核心组成部分，自竣工验收备案与物业承接查验完成至建筑物功能性退役为止。按照《物业管理条例》《住宅专项维修资金管理办法》《特种设备安全法》《公共建筑节能条例》等法规体系，运维阶段涉及空间管理、设备维保、能耗管理、安全管理、应急响应、改扩建支持等多个并行的工作流。

运维阶段的 BIM 数据有三个与前三阶段截然不同的特征。其一是**长期性**：运维数据要服务建筑物的整个使用寿命，而非项目周期；其二是**动态性**：运维数据持续被修订（设备更换、空间改造、租户变更等），而非"冻结的归档版本"；其三是**消费多样性**：运维数据需要服务多种异构系统（FM/CAFM/IWMS、楼宇自控、能耗监测、消防应急、物业管理 App 等），而非单一交付平台。

这三个特征决定了运维 BIM 与设计施工 BIM 在数据组织、工具链、维护机制上有本质差异。运维 BIM 不是把竣工模型搬到运维平台显示，而是要按运维场景重组数据、轻量化表达、对接多个系统、建立持续维护机制。这一差异未被充分理解，是国内运维 BIM 应用难以见到实效的根本原因之一。

需要说明的是，《建筑信息模型交付标准（草案）》（V2.0 草案）当前对运维阶段的交付物未做独立条文规定，本章基于 ISO 19650-3:2020 资产运营阶段的方法学并结合中国物业管理与设施管理实践推导而来。后续 V2.0 草案若增补运维阶段条文，本章相应内容应以草案最终版为准。

### 9.1.2 三重交付价值

运维阶段的 BIM 应用应同时实现三重价值。

第一重是**资产管理价值（Asset Management）**。运维方需要对建筑物内的所有资产（设备、空间、构件）实现"看得见、查得到、管得起"。BIM 模型作为资产的可视化容器，把分散在各类清单、合同、保修单、维护记录中的资产信息整合到统一的几何与属性框架中，支持按设备、按空间、按系统的多维度查询与管理。这一价值的实现，要求竣工移交阶段的资产数据完整可信。

第二重是**运营效率价值（Operational Efficiency）**。运维工作的高效与否直接影响建筑物的使用成本与服务质量。BIM 在运维阶段可支持空间快速配置（租户变更、功能调整）、维保任务自动派发、备件库存优化、应急响应快速定位、能耗诊断与优化等高频应用。这一价值要求 BIM 平台与日常运维工具（工单系统、楼宇自控、能耗监测系统等）有顺畅的数据交互。

第三重是**资产保值与改造支持价值（Value Preservation & Renovation Support）**。建筑物在使用过程中会经历若干次改造（小到机电改造、装修翻新，大到建筑功能转换、结构加固）。BIM 数据若能持续维护至改造时点，将极大降低改造的前期勘察成本与设计周期，并为改造决策提供更可靠的现状数据。这一价值要求运维 BIM 数据有持续的"修订与对齐"机制。

## 9.2 信息需求与典型应用

### 9.2.1 信息需求方与典型用例

运维阶段的信息需求方相比项目阶段有显著简化，主要集中在运维方与建设方两端，但每一方内部又有多个细分角色。

**物业管理单位**是日常运维的执行主体。其典型需求是基于轻量化模型快速完成空间查询、设备定位、维保派单、应急响应等高频任务；可验证的形态是"物业前台或巡检员通过移动端 App 在 30 秒内完成一次设备查询或空间定位"。

**设施管理团队**（在大型公共建筑、产业园区、企业总部中常设）关心的是设施的整体运行状态、能耗趋势、维保成本、租赁收益等管理性指标。其典型需求是基于 BIM 数据的多维度分析报表；可验证的形态是"月度设施管理报告基于 BIM 平台自动生成，覆盖空间利用率、维保完成率、能耗指标、设备故障率等核心指标"。

**业主或资产持有人**关心的是资产的整体价值与长期回报。其典型需求是建筑物的资产清册、估值数据、改造潜力评估等战略性信息；可验证的形态是"资产清册可随设备进出、空间变更动态更新，支持季度或年度的资产盘点"。

**特种设备管理单位**（电梯维保、压力容器检验、消防设施维保等）关心的是各自管辖的特种设备的状态与维护记录。其典型需求是按设备查询位置、查询历史维护记录、查询下次检验日期等。

**应急响应人员**（消防、安保、医疗等）关心的是建筑物的应急资源（消防设施、疏散通道、AED 设备、应急照明等）的位置与状态。其典型需求是在紧急情况下能在 30 秒内调出最近的应急资源位置；可验证的形态是"通过移动端 App 输入当前位置或扫描楼层标识，自动显示周边 50 米内的应急资源"。

**租户或终端用户**关心的是与自己使用空间相关的报修、变更、增值服务等。在新型智慧建筑中，租户可通过移动端 App 提交报修、查询当前空间的环境数据、申请会议室预订等，这些功能的底层数据均依赖 BIM 模型与传感器数据的整合。

### 9.2.2 典型应用场景

运维阶段的 BIM 典型应用可归纳为五大场景。

**场景 1：空间管理（Space Management）。** 包括空间属性维护（楼层、房间编号、面积、功能、租户）、空间分配与调整（租赁记录、工位分配）、空间利用率分析（结合人员定位与门禁数据）、空间改造支持（基于现状数据的改造方案推演）。空间管理是 BIM 在运维阶段最直接、最高频的应用，几乎所有 FM/CAFM/IWMS 系统都把空间模块作为核心功能。

**场景 2：设备运维（Equipment Maintenance）。** 包括预防性维护（按维护周期自动生成工单）、故障维修（基于设备位置与历史记录快速定位）、备件管理（按设备型号自动匹配备件）、设备生命周期管理（从安装到退役的全周期记录）。设备运维是 BIM 价值最易量化的场景，规模化应用后通常可降低 15% 至 30% 的维保成本。

**场景 3：能耗监测与优化（Energy Monitoring & Optimization）。** 包括能耗数据接入（电、水、燃气、热量等仪表数据通过 BMS 或 IoT 网关接入）、能耗按空间或按设备的归集分析、能耗异常预警、能耗优化建议（基于历史数据的对标与诊断）。这一场景在国内对接《公共建筑节能条例》与各地的能耗监测平台强制要求。

**场景 4：应急管理（Emergency Management）。** 包括消防资源定位（喷淋、烟感、灭火器、防火门、消火栓等）、疏散路径规划与可视化（动态计算最优路径）、应急预案演练（基于 BIM 的虚拟演练）、事件响应与回溯（事故现场的实时定位与事后复盘）。这一场景在大型公共建筑、医院、地铁、机场等高风险场所应用价值显著。

**场景 5：改造与翻新（Renovation & Refurbishment）。** 包括基于现状 BIM 的改造方案设计（避免重新勘察）、改造影响评估（结构、机电、消防的牵连影响）、改造过程的临时变化记录（保持运维 BIM 与现场同步）。这一场景把 BIM 从运维数据消费者重新转回项目数据生产者，体现了 BIM 全生命周期的循环价值。

## 9.3 关键技术与方法

### 9.3.1 运维 BIM 的轻量化与多端访问

竣工阶段移交的 BIM 模型通常体量巨大（数 GB 至数十 GB），原生格式（如 .rvt）需要专业软件打开，无法直接用于日常运维。运维 BIM 的第一项关键技术任务，就是把竣工模型轻量化并适配多端访问。

**轻量化的常见技术路径**：将原生模型或 IFC 转换为 Web 友好的轻量格式（glTF、3D Tiles、FBX 等），通常通过专用转换工具或运维平台的内置转换器完成。转换过程中通常会做几何简化（合并近似面、剔除运维无关的细节）、纹理压缩、属性精简等优化。转换后的模型体积通常仅为原模型的 5% 至 15%，但仍保留运维所需的核心几何与属性。

**多端访问的常见架构**：包括 Web 端（PC 浏览器，主要用于办公室管理）、移动端（iOS/Android App，主要用于现场巡检与应急响应）、大屏端（监控中心的展示终端）三种。三端的 BIM 数据应来自同一份后台数据，通过 RESTful API 与 WebSocket 等接口与后台同步。

**主流运维 BIM 平台**：国际产品包括 Autodesk Tandem、Bentley iTwin、Dassault 3DEXPERIENCE 等，这些平台覆盖竣工模型至运维数字资产的全流程能力，但价格较高、本地化适配有限。国内产品包括广联达 BIM 运维、上海蔚星科技、杭州海康威视设施管理、厦门朗新设施运维、品茗运维 BIM、北京筑龙运维平台等，这些平台多按 SaaS 或私有部署方式提供，本地化程度较高且价格较为友好。开源方案包括基于 Forge（现 Autodesk Platform Services, APS）的二次开发、基于 BIMServer 的开源部署、基于 IFC.js 的 Web 端轻量化方案等。

> **操作要点（基于 Autodesk Platform Services 的运维 BIM 部署，供参考）**
>
> 1. **模型上传**。把竣工 As-Built 模型（.rvt 或 .ifc）上传至 APS 的 Object Storage Service（OSS），获取唯一 URN。
> 2. **模型转换**。调用 Model Derivative API 把模型转换为 SVF 或 SVF2 轻量化格式（这是 Autodesk Viewer 使用的内部格式）。
> 3. **嵌入 Viewer**。在自建的运维 Web 平台或移动 App 中通过 Forge Viewer JavaScript SDK 嵌入模型查看器，加载已转换的 SVF 模型。
> 4. **属性扩展**。通过 APS 的 Properties API 读取模型构件的属性，并与运维数据库中的扩展属性（如维护记录、报修历史等）关联。
> 5. **交互配置**：实现"点击构件 → 弹出资产卡片"、"按系统过滤显示"、"按维保状态着色"等典型运维交互。
>
> 国内平台（广联达、蔚星、海康等）通常提供更"开箱即用"的体验，无需自行开发 Viewer 与 API 集成；但本地化平台的扩展灵活性与定制深度通常不及自建方案。中型与大型项目可考虑国内平台 + 部分自定义开发的混合模式。

### 9.3.2 BMS 与 IoT 数据的接入与融合

楼宇自控系统（Building Management System, BMS）与 IoT 传感器是运维 BIM 的"动态数据源"。BMS 监控空调、电梯、给排水、电力等核心系统的运行参数；IoT 传感器（温度、湿度、CO₂、人流量、占用状态等）补充更细粒度的环境与使用数据。把这些动态数据与 BIM 模型整合，是运维 BIM 从"静态查询"走向"动态运营"的核心技术。

**接入协议**：BMS 与 IoT 设备的常见通信协议包括 BACnet（楼宇自控行业标准）、Modbus（工业仪表与小型设备）、OPC UA（工业 4.0 标准）、MQTT（物联网轻量级协议）、HTTP/REST（互联网应用）。运维 BIM 平台需要内置或对接相应的协议适配器，把异构数据源的数据汇聚到统一的数据总线。

**数据建模**：把 BMS/IoT 数据点（Data Point）与 BIM 模型构件建立关联，是接入工作的核心。常见做法是在 BIM 模型构件的属性中增加"Data Point ID"字段，指向 BMS/IoT 系统中的对应点位；运维平台据此实现"点击模型构件 → 实时显示运行数据"。这一映射工作通常在系统调试阶段完成，应作为竣工移交的一部分由施工方与运维方共同建立。

**数据应用层**：包括实时监控（在 BIM 三维场景中以颜色或动画显示设备运行状态）、历史趋势分析（按时间序列分析能耗、温度、运行时长等）、异常预警（基于规则或机器学习识别异常模式）、设备健康度评估（结合运行参数与维护记录预测设备剩余寿命）。这些应用通常被合称为"数字孪生（Digital Twin）"在建筑运维中的具体形态，但与其纠结于概念名称，不如先把每一项应用做到运维方实际可用的水平。

> **操作要点（BMS 与 IoT 数据接入到运维 BIM 平台的典型流程）**
>
> 1. **梳理点位清单**。从 BMS 工程师（如对接 Honeywell Niagara、Schneider EcoStruxure、Johnson Controls Metasys、同方泰德、大金 BMS 等系统的工程师）处获取本项目的全部数据点位清单（Point List），通常以 Excel 形式提供，包含点位名称、所属设备、量纲、量程、报警阈值等字段。
> 2. **建立点位与构件映射**。在 BIM 模型中为每一类受监控的设备增加"Data Point ID"共享参数，把 BMS 点位的唯一标识符填入对应构件。这一动作通常由 BIM 协调员与 BMS 工程师配合完成，是接入工作量最大、最易出错的环节。
> 3. **配置协议适配器**。在运维 BIM 平台中按 BMS 的通信协议配置适配器：BACnet/IP（楼宇自控行业标准）走 UDP 47808 端口；Modbus TCP（工业仪表、变频器等）走 TCP 502 端口；OPC UA（高端工业系统）走 TCP 4840 端口；MQTT（物联网设备、移动 IoT 网关）走 TCP 1883 或 8883（TLS）端口。各端口的具体配置依平台与防火墙策略而定。
> 4. **联调验证**。在测试环境中接入若干典型点位，验证数据从 BMS 到运维 BIM 平台的端到端通路（数据更新频率、数值精度、报警触发等）；联调通过后再批量接入。
> 5. **建立运维交互**。在运维平台中配置"点击设备 → 弹出实时数据面板"、"按系统颜色着色"、"报警时三维高亮 + 弹窗提示"等典型交互。

数据接入工作量与建筑物规模成正比。一栋 5 万平方米的办公楼通常需要接入 3000 至 8000 个 BMS 点位，工作周期约 4 至 8 周；超大型公共建筑（如机场、大型综合体）的点位规模可达数十万级，需要专门的项目化推进。

### 9.3.3 工单与维保流程的 BIM 化

工单管理是运维工作的核心。传统的工单系统以文字描述定位故障（如"3 号楼 5 层 503 房间空调不制冷"），调度员据此派发任务，维修人员到场后才能确认具体设备型号、维护历史、备件需求。BIM 化的工单管理可在每个环节嵌入空间与设备数据，显著提升处置效率。

**报修环节**：租户或巡检人员通过移动端 App 在三维场景中点选故障位置，自动获取所在空间编号与可能的相关设备清单；选择具体故障设备后，App 自动填入设备型号、安装日期、上次维护日期、保修状态等关键信息。这一动作把传统报修单的填写时间从 5 至 10 分钟缩短至 1 分钟以内。

**调度环节**：调度员在 PC 端 Web 平台或大屏看到三维场景中所有未处理工单的位置标记，可按区域、按工种、按优先级做派发；派发时系统自动匹配最近的可用维修人员（结合人员定位数据）。

**执行环节**：维修人员在移动端接收工单后，App 自动显示故障设备的位置（在三维场景中高亮）、维护历史、操作手册、备件清单。维修过程中可拍照记录、扫描备件二维码出库、填写维修结果，所有数据实时同步至运维平台并与 BIM 模型构件关联。

**回溯环节**：故障处置完成后，所有维修记录沉淀为该设备的"运维档案"，可在后续的预防性维护、设备评估、报废决策中被调用。

> **操作要点（基于运维平台的 BIM 化工单流程示例）**
>
> 1. **工单触发**。通过移动端报修、BMS 自动报警、定期维护计划等渠道触发工单。
> 2. **工单关联资产**。系统自动或人工把工单关联到 BIM 模型中的具体设备 GUID，调出该设备的所有相关信息。
> 3. **工单派发**。调度员或自动派发系统按规则（最近的可用人员、技能匹配、优先级等）派发工单。
> 4. **现场处置**。维修人员在移动端获取工单与设备信息，到场后扫描设备二维码确认，按操作手册执行维修。
> 5. **工单关闭**。维修完成后填写结果，上传现场照片，由调度员或主管审核关闭。
> 6. **数据沉淀**。工单数据与设备 BIM 构件关联归档，成为该设备运维档案的一部分；高频故障的设备可触发预防性维护或更换决策。

工单 BIM 化的实施关键不在技术，而在**数据基础与人员习惯**。数据基础方面，要求竣工移交时移交的设备资产清单完整、关联文档齐全；人员习惯方面，要求维修人员真正使用移动端而非沿用纸质单据，这通常需要数月的培训与监督期才能形成。

### 9.3.4 能耗监测与优化

公共建筑能耗监测在中国是强制性要求。《公共建筑节能条例》与《国家机关办公建筑和大型公共建筑能耗监测系统建设、验收与运行管理规范》要求大型公共建筑（通常 2 万平方米以上）建立能耗监测系统，并按规定向建设主管部门上报数据。BIM 平台可作为能耗监测数据的可视化与分析载体。

**能耗数据接入**：通过 BMS 或独立的能耗监测系统接入电、水、燃气、热量等仪表数据。能耗仪表的安装位置（按楼层、按区域、按系统）应在设计阶段就规划合理，否则后期分项计量会有困难。每一只仪表应在 BIM 模型中有对应的虚拟构件，并通过 Data Point ID 与实际仪表关联。

**能耗按维度归集**：包括按时间（小时、日、月、年）、按空间（楼层、房间、租户区）、按系统（空调、照明、动力、特殊用电）、按用户（按租户、按部门）等维度。这些归集结果是能耗分析与对标的基础。

**能耗诊断与优化**：基于历史数据识别能耗异常（如某区域能耗突然攀升）、对标分析（与同类建筑或本建筑历史同期对比）、负载分析（设备运行时长与负载率）、节能潜力评估（识别可优化的设备与策略）。这些诊断为运维方做出运行参数调整、设备升级、租户行为引导等决策提供依据。

**与节能监管的对接**：按地方主管部门要求向能耗监测平台上报数据。多数省市的能耗监测平台已接受标准格式的能耗数据上报，BIM 平台只需配置数据导出接口即可对接。具体上报格式（XML 或专用 JSON）应在项目所在省市的能耗监测平台技术对接文档中确认；《国家机关办公建筑和大型公共建筑能源消耗数据采集技术导则》对中央层级的数据采集格式有规定，地方平台通常在此基础上做扩展。

> **操作要点（基于运维 BIM 平台的能耗看板配置）**
>
> 1. **配置仪表台账**。在 BIM 模型中为每一只能耗仪表（电、水、燃气、热量等）增加"仪表编号、所属分项、所属空间、量程、采样频率"共享参数；把仪表与对应的 BMS 数据点位建立映射（通过 § 9.3.2 的 Data Point ID 机制）。
> 2. **定义分项归集规则**。按本项目的能耗分项体系（典型为照明插座、空调、动力、特殊用电四级分项）配置归集规则。每只仪表归属于一个或多个分项，归集时按权重做加权汇总（避免重复计量）。
> 3. **配置可视化看板**。在运维平台（如广联达 BIM 运维、蔚星智慧楼宇平台、自建 APS Viewer 等）中创建能耗看板，包含：本月总能耗（与去年同期对比）、按分项能耗占比（饼图）、按时间能耗趋势（折线图）、按区域热力图（在 BIM 三维场景中用颜色显示各区域能耗强度）、TOP 10 高能耗设备排行（表格）。
> 4. **配置异常预警规则**。按"日同比 ≥ 30%"或"周同比 ≥ 20%"等阈值设置预警规则，触发时自动向能耗管理员发送邮件或 App 推送，并在 BIM 三维场景中标识异常区域。
> 5. **配置月报自动生成**。按月度自动汇总数据生成能耗分析报告 PDF，包含本章 § 9.5.3 列出的核心指标，作为节能管理与对外上报的依据。
> 6. **能耗强度对标**。把本建筑的单位面积能耗（kWh/m²·月）与本市同类建筑的平均水平、本建筑历史同期、行业标杆值等做对标分析，识别节能潜力区间。

### 9.3.5 数据持续维护机制

运维阶段最容易被低估的工作，是 BIM 数据的"持续维护"。建筑物在使用过程中会持续发生变化：设备更换、空间改造、租户变更、装修翻新、临时设施搭建等。如果 BIM 数据不能与现场同步，将逐渐失去其作为"现状数据基底"的价值，最终回到与传统纸质资料类似的境地。

**维护机制的三个层次**。第一层是**例行维护**，配合日常工单的更新（设备更换、维护记录追加等），由运维方一线人员通过移动端在工作过程中自然完成。这一层维护成本最低，是基础。第二层是**周期维护**，按月度或季度组织对 BIM 数据做集中盘点与修订，覆盖一些非工单触发的变化（如租户布局微调、临时设施调整等），由 BIM 运维专员主导。第三层是**重大维护**，配合改造、翻新、加固等较大规模的现场变化做模型重构，通常作为独立项目（小型改造项目）执行，由建设方或物业方组织。

**维护责任与成本**：BIM 数据的持续维护需要专门的预算与人员。常见配置是每 5 万平方米的运维场所配置一名 BIM 运维专员（兼职或全职视情况而定），并把 BIM 维护工作纳入运维方的年度预算。如果运维方自身能力有限，可委托第三方 BIM 服务商提供持续维护服务。

**与改造项目的衔接**：当建筑物进入改造阶段，运维 BIM 应作为现状数据基底交付给改造项目的设计与施工方。改造完成后的更新模型应交还给运维方，纳入持续维护循环。这一循环若能建立，BIM 全生命周期的价值才真正实现。

## 9.4 实施步骤与角色责任

### 9.4.1 运维 BIM 的启用与运行节奏

运维 BIM 的实施可分为"启用、稳定运行、长期维护"三阶段。

**启用阶段（运维起始 0 至 6 个月）**。重点工作包括：（1）从竣工移交方接收数字资产，验证数据完整性；（2）部署运维 BIM 平台，完成轻量化模型上传与界面定制；（3）与 BMS、能耗监测、工单系统、安防系统等周边系统做接口对接；（4）对运维方人员（物业前台、巡检员、维修工、管理岗等）做分层培训；（5）启动若干高价值场景的试运行（如设备维保、空间管理）。本阶段的关键是形成可用的运维 BIM 工作环境，而不是追求全场景落地。

**稳定运行阶段（启用 6 个月后至若干年）**。重点工作包括：（1）扩展应用场景至能耗管理、应急管理、改造支持等更高阶应用；（2）建立 BIM 数据的例行维护机制，把工单触发的设备更新、空间调整等自然纳入维护流程；（3）按季度或年度评估 BIM 应用的业务效果与数据质量，迭代优化；（4）逐步向租户、业主等扩展用户群，扩大 BIM 价值面。

**长期维护阶段（若干年后至建筑物退役）**。重点工作包括：（1）定期（建议每 3 至 5 年）对 BIM 数据做大规模盘点与修订，覆盖累积的现场变化；（2）配合改造翻新做模型重构与回流；（3）在产权变更、运营方更替等节点做数据完整性审计；（4）在建筑物功能性退役时配合做拆除评估或资产回收。

### 9.4.2 角色责任矩阵

运维阶段的核心角色及其责任分布与项目阶段有显著差异，主要在运维方内部细分。

**业主或资产持有人**对 BIM 数据的整体战略与长期投入承担"A"责任，决定 BIM 平台的选型、运维 BIM 团队的预算、BIM 数据的维护标准等。

**物业管理负责人或设施管理总监**对运维 BIM 的日常应用与运营效果承担"R/A"双重责任，组织各业务线的 BIM 应用、协调与建设方的接口对接、监督维护工作的执行。

**BIM 运维专员（或主管）**（角色定位上承接项目期由建设方 BIM 经理把控的数字资产管理职责，但工作重心从"项目交付"转向"长期运营"）对 BIM 平台的技术运行、数据维护、用户支持承担"R"责任，是运维 BIM 的核心执行人。在大型设施中可能配备 2 至 5 人的团队，分别负责数据维护、应用支持、新场景开发。

**一线运维人员**（巡检员、维修工、客服人员等）是 BIM 应用的高频用户，通过移动端在日常工作中使用 BIM 数据。其使用习惯的形成，是 BIM 价值能否实现的关键。

**租户或终端用户**在新型智慧建筑中可能直接接入运维 BIM（通过租户 App、报修系统等），对 BIM 数据有有限的查询权限与反馈渠道。

**第三方维保单位**（电梯维保、消防维保、空调维保等）应在 BIM 平台上获得有限的访问权限，能够查询与本职工作相关的设备信息与维护历史，并把维护记录回传至 BIM 平台。

### 9.4.3 与第 8 章和前序章节的衔接

本章的输入完全依赖于 [第 8 章](08_Handover_Assets.md) 竣工移交阶段的数字资产；竣工移交质量决定运维 BIM 的起点高度。本章不重复竣工移交的方法与流程，而是聚焦运维阶段独有的：轻量化与多端、BMS/IoT 融合、工单 BIM 化、能耗监测、数据持续维护。

运维 BIM 的应用方法学也参照 [第 5 章](05X_Delivery_Implementation.md) 的实施指南，但需要做"项目逻辑到运营逻辑"的转译：项目阶段的 EIR/BEP/MIDP 在运维阶段对应"运维 BIM 应用规划/年度运维 BIM 工作计划/月度数据维护计划"等文档。运维方应在接收数字资产后的最初 3 至 6 个月内编制本机构的"运维 BIM 应用规划"，作为后续工作的纲领。

## 9.5 中国工程语境下的特殊约束

运维阶段在中国有独特的法规框架与管理实践。以下五项本地约束需要在 BIM 工作中正面应对。

### 9.5.1 物业管理与承接查验

《物业管理条例》《物业承接查验办法》对物业管理单位的承接查验、日常服务、专项服务等提出了具体要求。物业管理单位是大多数住宅与商业建筑的主要运维执行主体，其工作模式与服务范围受到法规约束。

BIM 在物业管理中的应用应对应物业服务的具体内容：共用部位与共用设施设备的查验与维护、电梯运行、消防设施巡检、水箱清洗、外立面维护、绿地养护等。每一项服务都可通过 BIM 平台关联到具体的设施设备与空间位置，作为服务记录的可追溯依据。

对应的 BIM 工作纪律是把物业服务的标准作业流程（SOP）映射到 BIM 平台。例如，电梯日常巡检的 SOP 包括"检查机房环境、检查驱动电机、检查门系统、检查安全保护、检查应急通讯"等，每一项可在移动端 App 中作为复选项，巡检员逐项确认并拍照后即生成本次巡检的完整记录。这一做法相比传统的纸质巡检表在数据可分析性、问题可追溯性上有显著提升。

### 9.5.2 特种设备管理

《特种设备安全法》对电梯、压力容器、起重机械、压力管道、大型游乐设施等特种设备的设计、制造、安装、使用、检验、维护、报废全过程提出了严格的管理要求。每一台特种设备在投入使用前需向特种设备安全监督管理部门办理使用登记，定期接受法定检验，由具备资质的维保单位提供日常维保服务。

BIM 在特种设备管理中的价值是把每一台特种设备的全周期信息结构化保存。具体包括：设备登记证号、生产厂家、型号、出厂日期、安装日期、首次检验日期、下次检验日期、维保单位、维保周期、维保记录、故障记录、改造记录等。这些信息应在竣工移交时完整收集并随设备模型构件归档，运维阶段持续更新。

对应的 BIM 工作纪律是在特种设备清单中建立"检验到期预警"机制。运维 BIM 平台应根据每台设备的下次检验日期，在到期前 30 至 60 天向运维负责人发送预警，避免漏检导致的合规风险。这一机制相比传统的台账管理在主动性与覆盖完整性上有显著优势。

### 9.5.3 公共建筑能耗监测

《公共建筑节能条例》与各省市的能耗监测平台建设要求，构成了国内大型公共建筑必须遵守的能耗监测体系。能耗监测的实施要求按照《公共建筑能耗远程监测系统技术规程》（JGJ/T 285-2014）等规范执行，包括分项计量仪表的配置、数据采集网关的部署、数据上报频率与格式等具体技术要求。

BIM 在能耗监测中的价值是把分散的能耗仪表数据与可视化的建筑空间关联，使能耗分析从"按楼栋看总量"提升到"按楼层、按区域、按租户、按设备分类型看分项"的精细化水平。这一价值的实现，要求竣工阶段的能耗仪表配置已经合理（覆盖关键分项），且每只仪表已与 BIM 模型构件建立关联。

对应的 BIM 工作纪律是在运维 BIM 平台中配置"能耗按维度看板"，定期（建议月度）生成能耗分析报告，识别异常区域与节能潜力。报告应至少覆盖：本月总能耗（与去年同期对比）、按分项的能耗占比、能耗强度（kWh/m²·月）的同期对比、TOP 10 高能耗设备清单、能耗异常事件清单。报告作为节能管理的依据并按规定上报地方主管部门。

### 9.5.4 应急管理与公共安全

《突发事件应对法》《消防法》《反恐怖主义法》等对公共建筑（特别是地铁、机场、医院、商场、学校等人员密集场所）的应急管理、消防安全、反恐安保提出了具体要求。运维方需要建立应急预案、定期演练、配置应急资源、建立指挥体系等。

BIM 在应急管理中的价值是把建筑物的所有应急资源（消防设施、疏散通道、AED 设备、应急照明、避难空间等）与现场实时数据（人员位置、烟感报警、视频监控等）整合到统一的可视化平台，支持应急响应的快速决策与资源调度。在大型公共建筑与高风险场所，这一应用的价值远超普通运维场景。

对应的 BIM 工作纪律是在运维 BIM 平台中配置"应急响应模块"，包括：（1）应急资源的快速查询（按类型、按区域、按状态）；（2）疏散路径的动态计算（考虑当前的火灾位置、人员密度、设施可用性）；（3）应急预案的可视化展示与演练支持；（4）事件响应的实时记录与事后复盘。这一模块应与建筑的消防控制室、安保监控中心做硬连接，在紧急情况下能成为指挥决策的核心工具。

> **操作要点（运维 BIM 平台的应急响应模块配置）**
>
> 1. **应急资源属性补全**。在 BIM 模型中确认所有消防设施（喷淋头、烟感、温感、消火栓、灭火器箱、防火门、防火卷帘等）、应急照明、AED 设备、避难空间、疏散通道、应急广播扬声器等已录入完整属性（位置、规格、状态、上次维护日期、责任维保单位）。
> 2. **接入消防控制室点位**。通过 BACnet、Modbus 或 Modbus over RS-485 协议把消防控制室的报警主机数据点位接入 BIM 平台。每一个烟感、温感、手报按钮在 BIM 模型中应有对应构件并通过 Data Point ID 与控制室主机点位映射；触发报警时三维场景中对应位置自动高亮、弹出报警信息卡片。
> 3. **配置疏散路径算法**。基于建筑物的疏散通道与门洞拓扑（在 BIM 模型中通过 IfcSpace 与 IfcDoor 的关系自动构建图结构），实现按"当前位置 + 火灾位置 + 通道可用性"三因素动态计算最短安全路径。常用算法是 Dijkstra 或 A* 的变体，已有若干运维平台内置该能力。
> 4. **与安保系统集成**。把视频监控（如海康威视、大华、华为好望等品牌的 NVR 系统）的摄像机点位与 BIM 模型构件建立映射；点击模型中某摄像机即可调出对应实时视频流。视频协议常用 ONVIF 标准。
> 5. **配置应急演练模式**。在 BIM 平台中预设若干典型应急场景（如某楼层中庭起火、某机房漏水、某大堂拥挤等），支持演练时一键触发场景，组织人员按 BIM 平台显示的预案流程做演练。演练完成后系统自动生成演练记录与改进建议。
> 6. **建立事件响应日志**。每一次实际事件（火警、漏水、设备故障等）应在 BIM 平台中留下完整记录（触发时间、触发位置、响应过程、处置结果、复盘结论），作为后续应急能力评估与预案优化的依据。

### 9.5.5 改造翻新与产权变更

中国工程建设进入存量提质阶段后，既有建筑改造、城市更新、产业园区翻新等成为工程市场的重要部分。在这些改造项目中，准确的现状数据是设计与施工的前提，BIM 模型的延续性与可信度直接决定改造的效率与成本。

对应的 BIM 工作纪律有两条。其一是**改造前的数据交付**：当建筑物进入改造决策阶段，运维方应向建设方与改造设计单位移交完整的运维 BIM 数据（含累积的修订记录、设备更换记录、空间调整记录），作为改造的现状基础。这一交付的质量取决于运维阶段的数据维护机制是否健全。其二是**改造后的数据回流**：改造项目完成后，新版的设计与施工 BIM 数据应回流至运维方，与原有运维 BIM 做合并与版本更新。这一回流的责任与流程应在改造项目的合同中明确写入，否则容易出现"改造完成、运维数据脱节"的常见困境。

产权变更（如建筑物转让、租赁主体变更等）时，运维 BIM 数据应作为资产移交的一部分。新业主或新租户接收数据后，应在原有数据基础上继续维护，而非重新建模或抛弃数据。这一连续性的实现，要求运维 BIM 数据有标准化的格式与文档说明，便于新接收方理解与使用。

## 9.6 常见失败模式与纠偏

运维阶段最具代表性的失败模式有以下三类。

第一类是**运维 BIM 沦为"展示工具"**。表现为运维方部署了 BIM 平台、上线了三维展示大屏，但日常运维仍按传统方式进行（纸质工单、电话调度、Excel 台账），BIM 平台仅在领导参观或项目汇报时启用。这一失败的根源是 BIM 平台未与日常运维工作流真正打通，仅作为可视化的"皮肤"。识别这一失败模式的简单测试是在运维方随机调阅一周的工单记录，查看其中通过 BIM 平台发起或处置的比例；比例低于 30% 的视为存在此问题。纠偏路径有三条：把 BIM 平台与既有的工单系统、巡检 App、能耗监测系统做硬性集成而非松散对接；在运维方人员的考核中纳入 BIM 平台的使用率指标；定期组织一线人员做使用反馈会议并据此优化平台体验。

第二类是**数字资产移交后无人维护**。表现为竣工移交时数字资产完整、模型可用，但移交后随着设备更换、空间调整、租户变更等持续变化，BIM 数据逐渐与现场脱节，3 至 5 年后已无法用作可信的现状参考。这一失败的根源是没有建立 BIM 数据的持续维护机制，数据维护工作未纳入运维方的常态预算与责任分工。纠偏路径是在接收数字资产时即建立"BIM 数据维护规则"：明确什么变化必须更新模型、由谁负责更新、按什么节奏更新、由谁审核更新质量。运维方应配备专职或兼职的 BIM 运维专员，并把这一岗位纳入运维方的组织架构与年度预算。

第三类是**BMS/IoT 数据与 BIM 模型"两张皮"**。表现为运维方部署了完整的 BMS 与 IoT 系统采集大量动态数据，也部署了运维 BIM 平台展示几何与属性，但两者各自独立运行，数据不能在统一界面中关联展示，也不能联动分析。这一失败的根源是接入工作未在系统选型与实施阶段做出整合规划，各子系统按各自厂商的方案部署，事后再做集成成本极高。纠偏路径有两条：在竣工移交前的运维方平台选型阶段就要求 BIM 平台必须支持主流 BMS/IoT 协议（BACnet、Modbus、OPC UA、MQTT 等）的接入；在系统集成的合同条款中明确数据点位映射的责任与交付物。已经形成"两张皮"的项目，可考虑通过中间件（数据总线）做事后整合，但成本与周期都会显著增加。
